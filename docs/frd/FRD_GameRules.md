# FRD - 遊戲規則 (Game Rules)

*對應原始碼：`src/game/pieces.js`、`src/game/useGame.js`*

---

## 1. 模組概述 (Module Overview)

### 模組目的
定義 Triple Town CL 的核心遊戲規則：物件合成鏈、放置與合成判定、熊（敵人）AI 行為、抽牌機率、商店經濟系統。這是遊戲平衡與可玩性的根本依據——調整任何數值前必須先對照本文件，避免破壞平衡（例如忍者熊出現率與清除手段的相對關係）。

### 主要用戶
- 玩家：透過遊戲互動間接體驗這些規則
- 開發者：新增物件、調整平衡、修 bug 時的規則依據

### 模組依賴
- `pieces.js`：靜態資料（物件定義、合成表、機率池），無狀態
- `useGame.js`：唯一的遊戲狀態來源（Composable），實作本文件所有規則
- `GameBoard.vue` / `GameCell.vue`：規則的視覺呈現（合成閃光、高級版外觀等）

## 2. User Stories

---

### US-01: 物件合成鏈

**Story 描述**:
- **As a** 玩家
- **I want to** 把 3 個同類物件放在相鄰位置
- **So that** 合成升級為下一階物件並獲得分數

**Story 狀態**: Done
**首次加入 Sprint**: 初版

#### Acceptance Criteria

- **AC-01-1**: 當某格放置的物件與上下左右相鄰格形成同類型連通群，且連通群數量 ≥ 3（`MERGE_COUNT` 例外表另有規定）時，系統應該將整群消除並在放置格生成合成結果物件
- **AC-01-2**: 合成後應該獲得 `PIECES[結果物件].score` 分數；若結果物件帶 `coins` 屬性（如寶箱），同時獲得金幣
- **AC-01-3**: 合成結果若能繼續與其他同類物件連通觸發下一輪合成（連鎖），系統應該遞迴處理直到無法再合成
- **AC-01-4**: 一次合成的連通群數量超過所需數量（4+）時，系統應該給予雙倍分數，且結果物件若屬於 `PREMIUM_PIECES` 集合，改用高級版（閃亮）外觀

#### 業務規則

**建築合成鏈**（9 階，score 依 tier 遞增）：
```
grass → bush → tree → hut → house → mansion → castle → floating_castle → triple_castle
 20     60    200    600   2000    6000    20000     60000            300000
```

**墓碑合成鏈**（由熊被困產生的起點）：
```
tombstone → church → cathedral → treasure（僅能點擊開箱，Standard Map 不再往下合成 large_treasure）
    0        10000     30000       0（開箱得 5000 金幣）
```

**石頭合成鏈**（僅由水晶合成失敗產生，不在一般抽牌池）：
```
rock → mountain → treasure
 0      5000        —
```

- 預設合成所需數量為 3；`MERGE_COUNT` 表列出例外（目前 Standard Map 無例外，恆為 3）
- 高級版外觀僅 `bush`、`tree`、`hut`、`castle` 四種類型有專屬美術（`PREMIUM_PIECES` 集合）；其餘類型即使 4+ 合成也不換圖，但雙倍分數規則仍適用
- 高級版標記在該格素材被消耗（再次合成或被 bot 摧毀）時清除

### US-02: 放置判定與基本得分

**Story 描述**:
- **As a** 玩家
- **I want to** 把手上的物件放到棋盤空格
- **So that** 推進遊戲並累積分數

**Story 狀態**: Done
**首次加入 Sprint**: 初版

#### Acceptance Criteria

- **AC-02-1**: 當玩家點擊空格且該格非盤子格（0,0）時，系統應該放置手上的當前物件並消耗 1 步數
- **AC-02-2**: 每次成功放置，系統應該立即加上該物件的 `placeScore`（若定義）
- **AC-02-3**: 如果步數已耗盡（`turnsLeft <= 0`），點擊放置應該不消耗任何動作，並發出「Out of turns!」提示信號（`noTurns` 計數 +1）
- **AC-02-4**: 如果目標格已有物件（一般物件）或為空格（bot 物件），放置應該視為無效，不做任何改動

#### 業務規則
- `bot` 物件的放置規則相反於一般物件：只能放在**已有物件**的格子，放在空格無效
- 寶箱（`isOpenable`）物件可在任何時候被點擊開啟拿金幣，此動作**不消耗步數**、不需要手上有牌

### US-03: 水晶（Crystal）橋接合成

**Story 描述**:
- **As a** 玩家
- **I want to** 用水晶連接原本不相鄰的兩群同類物件
- **So that** 湊足合成數量，即使它們中間被水晶隔開

**Story 狀態**: Done
**首次加入 Sprint**: 初版

#### Acceptance Criteria

- **AC-03-1**: 水晶放置後，系統應該檢查其上下左右四個相鄰格，對每個存在且可合成的類型分別做連通群 flood-fill，並將**同類型**但透過水晶橋接的多個連通群聯集
- **AC-03-2**: 若任一類型的聯集大小達到該類型所需合成數量減一（因為水晶本身會補位），系統應該以該類型觸發合成；水晶格變為合成結果物件
- **AC-03-3**: 若多個類型同時滿足合成條件，系統應該選擇合成結果價值（`score + coins`）最高者
- **AC-03-4**: 若沒有任何相鄰類型滿足合成條件，水晶應該變成石頭（`rock`）

#### 業務規則
- 水晶本身消耗 `placeScore = 20`，變成石頭時不再額外得分
- flood-fill 前必須先將水晶格清空（設為 null），避免把水晶自己誤判為同類物件的一部分

### US-04: 熊與忍者熊的移動 AI

**Story 描述**:
- **As a** 玩家
- **I want to** 熊在每次我放置物件後自動移動
- **So that** 遊戲有動態威脅，需要策略性地圍困或清除牠們

**Story 狀態**: Done
**首次加入 Sprint**: 初版

#### Acceptance Criteria

- **AC-04-1**: 每次玩家放置動作完成後（合成處理之後），系統應該讓場上所有熊與忍者熊各移動一次，移動順序隨機打亂
- **AC-04-2**: 普通熊應該嘗試往隨機排序的四個方向之一移動到相鄰空格；若四個方向皆無空格，原地不動
- **AC-04-3**: 忍者熊應該瞬移到棋盤上任意隨機空格（不限相鄰）；若全盤無空格，原地不動並留待困住判定
- **AC-04-4**: 剛被玩家放置在棋盤上的熊，本回合不參與移動（避免放下瞬間就消失於視野外的違和感）

#### 業務規則
- 移動階段所有熊先各自處理完，才進入下一步的困住判定（避免處理順序影響移動結果）
- 忍者熊的瞬移是「原版行為」的還原：不可預測、無法用走位困住，是主要威脅來源

---

### US-05: 熊的困住判定與清除

**Story 描述**:
- **As a** 玩家
- **I want to** 把熊困在沒有出口的角落
- **So that** 牠們變成墓碑，可以進一步合成成教堂等高分建築

**Story 狀態**: Done
**首次加入 Sprint**: 初版

#### Acceptance Criteria

- **AC-05-1**: 系統應該以「連通熊群」（相鄰普通熊的集合）為判定單位，而非個別熊
- **AC-05-2**: 若整個熊群中**任何一隻**熊的相鄰格還有空格，整群都不算被困，繼續遊蕩
- **AC-05-3**: 只有當整群周圍完全沒有空格時，系統應該將群內所有熊**同時**轉為墓碑，並觸發合成判定
- **AC-05-4**: 忍者熊的困住條件不同：只有當「全盤無任何空格」（瞬移失敗）時才會困住轉為墓碑
- **AC-05-5**: 多隻熊同時被困、變成墓碑後若總數 ≥ 4，應該享受 US-01 的 4+ 合成雙倍分數規則

#### 業務規則
- 同時轉換（而非逐一）是刻意設計：讓一次困住 4 隻以上的熊能一次性合成並吃到 bonus，還原原版手機遊戲的手感
- 合成起點優先選擇玩家剛放置的格子（若在受困群內），讓教堂等結果物件傾向出現在玩家操作的位置，行為與一般合成一致
- 遊戲結束時（`finalizeBoard`）場上所有殘留的熊與忍者熊會被強制轉為墓碑並觸發合成，計入最終結算分數

### US-06: 抽牌機率池

**Story 描述**:
- **As a** 玩家
- **I want to** 每次抽到的物件遵循合理的機率分布
- **So that** 遊戲難度曲線符合原版設計（威脅與資源的平衡）

**Story 狀態**: Done
**首次加入 Sprint**: 初版

#### Acceptance Criteria

- **AC-06-1**: 系統應該用加權隨機（`weightedRandom`）從 `SPAWN_POOL` 抽取下一個物件，權重總和作為機率分母
- **AC-06-2**: 若商店購買佇列（`storeQueue`）非空，系統應該優先出佇列中的物件，而非走機率池
- **AC-06-3**: 石頭（`rock`）不應該出現在一般抽牌池中，僅能由水晶合成失敗產生

#### 業務規則

**機率池權重**（總權重 100）：

| 物件 | 權重 | 機率 | 備註 |
|---|---|---|---|
| grass | 44 | 44% | 最基礎的建築鏈起點 |
| bush | 20 | 20% | |
| bear | 13 | 13% | 主要威脅 |
| tree | 10 | 10% | |
| hut | 5 | 5% | |
| crystal | 4 | 4% | 特殊合成工具 |
| bot | 3 | 3% | 平均每 33 張出一隻——熊/忍者熊的清除手段 |
| ninja_bear | 1 | 1% | 平均每 100 張出一隻——無法被困住、永久累積 |

**平衡設計原則**：忍者熊無法用一般困住手段清除（只能等全盤滿），會持續累積佔用棋盤空間；因此清除手段 `bot`（3%）的出現頻率刻意設計為明顯高於忍者熊（1%），否則場上忍者熊數量會失控增長，破壞遊戲可玩性。**調整這兩個權重時必須同時考慮兩者的相對比例，不可單獨改動。**

### US-07: 商店經濟系統

**Story 描述**:
- **As a** 玩家
- **I want to** 用累積的金幣購買額外步數、特殊物件或悔棋
- **So that** 突破手氣不佳的局面，延長遊戲時間

**Story 狀態**: Done
**首次加入 Sprint**: 初版

#### Acceptance Criteria

- **AC-07-1**: 系統應該提供 7 種商店商品，各有獨立價格與庫存上限
- **AC-07-2**: 購買物件類商品後，該物件應該立即插入手牌佇列最前面優先出牌，原本的當前牌與下一張牌不會消失，退回佇列稍後仍會出現
- **AC-07-3**: 購買「Undo」應該還原到上一次放置動作前的完整棋盤狀態（分數、步數、手牌、高級版標記），但**不還原金幣**（避免寶箱金幣被重複領取的漏洞）
- **AC-07-4**: 若該局尚無任何放置動作（無可悔棋快照），Undo 購買應該失敗且不扣款
- **AC-07-5**: 各商品庫存於每局開始時重置為滿額；局內售完不再補貨

#### 業務規則

**商店商品表**：

| 商品 | 單價 | 每局庫存 | 效果 |
|---|---|---|---|
| 200 Turns | 950 | 不限購 | 立即增加 200 步數 |
| Crystal | 1500 | 4 | 加入手牌佇列 |
| Imperial Bot | 1000 | 4 | 加入手牌佇列 |
| Tree | 400 | 7 | 加入手牌佇列 |
| Bush | 150 | 7 | 加入手牌佇列 |
| Grass | 50 | 7 | 加入手牌佇列 |
| Undo | 75 | 不限購 | 還原上一步（需有快照） |

- 金幣為**跨局持久**貨幣：每局結束時的結算金幣會累加到下一局，開新局時不重置

### US-08: 遊戲結算與村莊等級

**Story 描述**:
- **As a** 玩家
- **I want to** 在棋盤填滿、遊戲結束時看到詳細的金幣結算
- **So that** 了解本局的收穫並規劃下一局的商店消費

**Story 狀態**: Done
**首次加入 Sprint**: 初版

#### Acceptance Criteria

- **AC-08-1**: 當棋盤沒有任何可放置的空格（`hasEmptyCell` 為否）時，系統應該結束遊戲並執行最終清算
- **AC-08-2**: 最終清算應該先將場上所有殘留的熊/忍者熊強制轉為墓碑並觸發合成，再計算結算金幣
- **AC-08-3**: 結算金幣應該包含三部分：村莊等級金幣、步數金幣（每步 1 金幣）、場上建築物分項金幣
- **AC-08-4**: 系統應該依場上最高階建築判定村莊等級標籤（如 Imperial City、Castle Town），並顯示在結算畫面
- **AC-08-5**: 完場分數應該寫入排行榜，只保留分數最高的 10 筆記錄

#### 業務規則

**村莊等級金幣** = 場上所有計分建築的 tier 總和 × 50（反映整個城鎮的整體發展程度，非單一最高建築）

**建築物分項金幣**（每個計入場上建築的固定單價）：

| 建築 | 每個金幣 |
|---|---|
| hut | 5 |
| house | 20 |
| mountain | 50 |
| church | 30 |
| cathedral | 150 |
| mansion | 100 |
| castle | 200 |
| treasure | 500 |
| floating_castle | 1000 |
| large_treasure | 2000 |
| triple_castle | 5000 |

**村莊等級標籤**（依場上是否存在對應建築，由高至低比對，取第一個符合者）：

```
triple_castle → Imperial City
floating_castle → Royal City
castle → Castle Town
mansion → Noble Estate
house → Township
hut → Settlement
tree → Hamlet
bush → Camp
（無以上任何建築）→ Outpost
```

## 3. 非功能需求 (Non-Functional Requirements)

### 效能需求
- 合成連鎖（`processMerges` 遞迴）與熊移動判定（`moveBears`）須在單次放置動作內同步完成，不可產生使用者可感知的延遲（原版凍結問題已知，見 SRD 技術債）
- 6×6 棋盤規模下，flood-fill 與困住判定的複雜度可忽略，無需優化

### 安全需求
不適用（純前端單機遊戲，無使用者資料或網路傳輸）。

### 可用性需求
- 合成閃光、高級版外觀、手牌智慧停放（優先提示可合成位置）為原版行為的還原，用於降低學習門檻
- 步數耗盡時的「Out of turns!」提示必須明確區分於當機，避免使用者誤判

## 4. 術語定義 (Glossary)

| 術語 | 定義 |
|------|------|
| tier | 建築階級數值，用於村莊等級金幣計算（tier 總和 × 50） |
| placeScore | 放置物件時立即獲得的基本分（非合成分） |
| 連通群 (connected group) | 透過 flood-fill 找出的相鄰同類型格子集合 |
| 高級版 (Premium) | 4+ 合成 bonus 產生的閃亮版外觀，僅 bush/tree/hut/castle 有專屬美術 |
| 橋接 (Bridge) | 水晶連接兩個原本不相鄰的同類連通群，使其可合併判定 |
| 熊群 (Bear Group) | 相鄰普通熊組成的連通群，困住判定以群為單位而非個體 |
| 瞬移 (Teleport) | 忍者熊每回合隨機跳到棋盤任意空格的移動方式 |
| Standard Map | 原版遊戲的標準規則集（本專案目前僅實作此規則集，無合成數量例外） |
